# Урок 4.1 — Сквозная аналитика: от клика до LTV

**Цель урока:** понять, как устроена сквозная аналитика — сшивка рекламных систем, сайта/приложения, CRM и транзакций; научиться строить юнит-таблицу пользователя и видеть, где рвётся цепочка данных.

**Перед уроком:** уроки 3.1–3.2 (каналы, UTM), 2.3 (LTV).

## Зачем это аналитику

Отдельные отчёты есть у всех: в Директе — клики, в Метрике — сессии, в CRM — заказы. Но вопрос бизнеса звучит сквозняком: «какой канал приводит людей, которые **покупают и остаются**?». Без сшивки каждый отчёт врёт по-своему: рекламный кабинет рапортует конверсии по своей атрибуции, CRM не знает источника, продукт не знает CAC. Сквозная аналитика — это не «купить сервис», а **дисциплина сшивки**: один пользователь — одна строка — вся его история от первого касания до LTV.

## Теория

### 1. Слои данных и их сшивка

```
Рекламные кабинеты (показы, клики, расходы)     ← по кампаниям/дням
        ↓ клик с UTM + идентификаторы (yclid/gclid)
Веб/приложение (сессии, события, device_id)     ← по пользователям
        ↓ авторизация / регистрация
Аккаунт (user_id) → CRM (сделки, оплаты)        ← по клиентам
        ↓
Юнит-таблица: user_id | каналы-касания | заказы | выручка | маржа | LTV
```

Ключи сшивки: **публичные идентификаторы клика** (yclid/gclid/fbclid — рекламная система «знает» свой клик), **cookie/device_id** (внутри браузера/устройства), **user_id после авторизации** (главный ключ), email/телефон (для офлайн-CRM). Задача — довести касания и транзакции до user_id: тогда LTV когорт по каналам (урок 2.3) считаются честно.

### 2. Юнит-таблица — сердце сквозной аналитики

Одна строка на пользователя: атрибуты (канал первого касания, источник регистрации, гео), события (заказы, выручка по месяцам), статусы (активен/ушёл). Из неё производятся все отчёты: CAC по каналам (джойн с расходами), LTV когорт (2.2–2.3), retention по каналам, атрибуция (4.2–4.3). Правила: идемпотентность (дубль события не создаёт юзера), версии определений (какая регистрация «считается»), история касаний хранится полностью (не только «первый/последний»).

### 3. Где рвётся цепочка

| Разрыв | Что теряем | Чем чиним |
|---|---|---|
| Кросс-девайс (смотрел с телефона, купил с компа) | цепочка касаний | авторизация как ключ; моделирование (4.3) |
| Блокировщики/ATT (iOS) | часть показов и кликов | агрегаты, MMM, гео (3.3) |
| Офлайн-покупки | транзакции мимо веба | CRM/касса → мэтчинг по карте/телефону |
| Окна атрибуции у платформ | платформа режет историю | хранить сырые касания у себя |
| Рекламные системы «не отдают» юзера | только макро-статистика | yclid/gclid + свои логи |
| Разные определения конверсии | споры о цифрах | единый словарь событий (метрик-хаб) |

### 4. CDP и идентификация

CDP (Customer Data Platform) — промышленная реализация сшивки: профили пользователей, stitch-правила (cookie→user_id при авторизации, email→профиль), сегменты наружу (в рекламные системы, CRM). Покупать CDP имеет смысл, когда источников много и команд больше трёх; до этого — своя юнит-таблица на базе хранилища (дешевле и прозрачнее).

## Разбор на данных

Сшивка «ЕдаДома» (учебный пример): 3 лога — клики (с yclid и UTM), сессии (cookie → user_id после регистрации), заказы (user_id). Правила: касания до регистрации приписываются юзеру по cookie; заказ мэтчится по user_id + дате; расходы — по кампании/дню. Результат-юнит-таблица: 40 тыс. юзеров, у 82% — ≥1 касание с UTM; 11% — «organic/direct» с историей показов (view-through — имён нет!); 7% — кросс-девайс потерян (меняли устройство до регистрации). Из таблицы: CAC по каналам, LTV90 когорт, retention по каналам — все отчёты М2–М3 одной QUERY. Отчётная находка: канал «таргет» при CAC 610 ₽ даёт LTV90 ниже органики — вопрос не в закупке, а в качестве аудитории.

## Подводные камни

1. **«Сквозная аналитика из коробки»** — чаще всего красивый отчёт по last-click; сверьте методику до покупки.
2. **Дубли идентичности** (два профиля одного человека) завышают CAC и занижают LTV; дедуп по email/телефону/карте.
3. **Смотрели показы — не кликали**: view-through касания не попадают в клик-логи — либо собирать показы (API), либо признать слепоту (4.3).
4. **Переопределение конверсии** каждой системой: платформа считает «клик→визит за 90 дней», вы — «регистрация→заказ за 14»; фиксируйте свой словарь.
5. **Приватность и согласия**: сшивка по персоналиям — только по правилам обработки данных (и аккуратно с iOS/ATT).

## Практика

Практика по уроку будет добавлена финальным блоком курса (сшивка трёх логов в юнит-таблицу на синтетике).

## Домашнее задание

1. Юзер: кликнул с телефона (не авторизовался), потом зашёл с ноутбука и купил после регистрации. Что увидит наивная сквозная аналитика и что — с авторизационной сшивкой?

<details>
<summary>Ответ</summary>

Наивная: два «пользователя» — анонимный мобильный клик и десктоп-покупатель (organic); конверсия уедет в organic, касание потеряно. С авторизационной сшивкой (user_id связан с обоими cookie задним числом) — один юзер: касание cpc → покупка; CAC посчитан верно.
</details>

2. Рекламный кабинет показывает 1000 конверсий, ваша сквозная — 640. Пять возможных причин.

<details>
<summary>Ответ</summary>

Разные определения конверсии и окна атрибуции; платформа считает post-view/дубли кликов; ваша сторона теряет события (блокировщики, обрыв сессии); дедуп юзеров схлопывает повторы; офлайн-конверсии видит только одна из систем. Алгоритм: сверить определения → посчитать расхождение по слоям (клики→сессии→заказы) → локализовать разрыв.
</details>

3. Зачем хранить все касания, а не только первый и последний источник?

<details>
<summary>Ответ</summary>

Атрибуция (4.2–4.3) — это перераспределение ценности по цепочке; модели (ML) учатся на полных путях; длина пути и повторы касаний — сами по себе фичи; при смене модели атрибуции историю не придётся собирать заново. «Первый/последний» — это уже готовые ответы, которые запрещают вопросы.
</details>

## Шпаргалка

1. Сквозная аналитика = дисциплина сшивки: кабинеты → веб/апп → CRM → юнит-таблица (user_id).
2. Ключи: yclid/gclid, cookie/device_id, авторизация (главный), email/телефон для офлайна.
3. Разрывы: кросс-девайс, блокировщики, офлайн, окна атрибуции — у каждого свой фикс, остаточная слепота признавайте явно.
4. CDP — промышленная сшивка; до трёх источников хватает своей юнит-таблицы.
5. Все отчёты (CAC, LTV когорт, retention каналов, атрибуция) — производные юнит-таблицы.
